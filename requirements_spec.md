## 1. Purpose and users
A free, local, point-and-click platform that lets a researcher run a complete, reproducible Mendelian randomization study — from choosing traits to a publication-ready report — without writing code and without any AI/API keys. Users: two researchers (macOS Apple Silicon and Windows 10/11), expert-level in epidemiology, not necessarily in R.

## 2. What the user does (user journey)
| Step | User action | What the app does automatically | What the user sees / receives |
|---|---|---|---|
| 1. Start | Open the app; create or reopen a **Project** | Checks dependencies, references, disk space, token | Project dashboard; health check (green/amber/red) |
| 2. Research question | Choose design: univariable, multivariable, mediation, bidirectional, **drug-target / cis-MR** (v1); multi-outcome/network/cross-population greyed as "v2" | Sets which later options are relevant | Plain-language summary of the question ("Effect of A on Y") |
| 3. Exposures & outcomes | Search & multi-select traits (and mediators) — or a **gene/protein** (QTL exposure) for drug-target MR | Searches the local catalogue (EFO-grouped), shows per-dataset cards | Dataset cards: source, ancestry badge (declared + inferred), N/cases, build, units passport, full-sumstats availability, overlap risk |
| 4. Population | Pick ancestry from the list the app offers | Shows only ancestries available for *all* chosen traits; flags mismatch | Ancestry choice + warnings (R13) |
| 5. Data check | Click **Prepare data** | Downloads/caches, harmonises, lifts builds, standardises units, estimates overlap (LDSC) | QC report: SNPs kept/dropped and why, units, overlap estimate |
| 6. Instruments | Accept defaults or open *Advanced* (p-threshold, clumping r²/kb, proxies, Steiger filtering) | Local clumping with PLINK + 1000G; computes F, conditional F, I²GX | Instrument table; strength summary; amber/red flags |
| 7. Methods | Pick a preset (**Quick / Standard / Comprehensive**) or tick methods | Feasibility engine (31 rules) enables, ambers or greys out each method with a reason; recommender ranks suitable methods | Method checklist with tooltips ("needs ≥3 IVs, found 2") |
| 8. Run | Click **Run** | Background jobs with progress, cancel, ETA; multiple-testing correction across pairs | Live progress panel |
| 9. Results | Explore | Combines estimates, heterogeneity, pleiotropy, direction tests; agreement summary | Interactive results dashboard (Section 3) |
| 10. Export | Click **Export** | Builds report, figures, tables, citations, recipe file | The deliverables package (Section 3) |

## 3. What the user receives (deliverables)
1. **Interactive results dashboard** — per exposure–outcome pair: estimate table for all methods (β/OR, 95% CI, P, units stated); forest plot across methods; scatter, funnel, leave-one-out, single-SNP and radial plots; MVMR effect plot; mediation diagram (total / direct / indirect, proportion mediated); "method agreement" panel (consistent direction & significance across methods with different assumptions).
2. **Diagnostics panel** — instrument strength (F, conditional F), heterogeneity (Cochran's Q, Rücker's Q′), Egger intercept, I²GX, MR-PRESSO global test and outliers, Steiger direction, sample-overlap estimate, ancestry checks — each with a traffic-light verdict and an explanation.
3. **Plain-language interpretation** — template-based text (no AI) summarising the main estimate, robustness and caveats.
4. **Report (HTML + PDF)** structured by the STROBE-MR checklist (PMID 34698778): question, data sources, instrument selection, methods, results, sensitivity analyses, limitations — with all figures and tables.
5. **Data exports** — CSV/Excel tables of instruments, harmonised data, every method's results and diagnostics; figures as PNG (300 dpi) and SVG/PDF.
6. **Citation list** — automatically generated references for every method, package and dataset actually used (from the inventory).
7. **Reproducibility bundle** — "analysis recipe" file (all choices + dataset IDs + versions + seeds) that re-runs the identical analysis on the other computer; package-version manifest; activity log.
8. **Saved project** — reopen, modify a step, and re-run only what changed.

## 4. Functional requirements
**Data & catalogue**
- FR-01 Build and refresh a local trait catalogue from OpenGWAS metadata (+ GWAS Catalog, FinnGen, Pan-UKB where available); EFO-grouped search; manual override table.
- FR-02 Per-dataset card: source, ID, trait/EFO, ancestry (declared + inferred via `bigsnpr::snp_ancestry_summary`), N, ncase/ncontrol, build, units passport, full-sumstats availability, contributing cohorts.
- FR-03 Offline-first cache of all downloads; download queue respecting the OpenGWAS 20-files/day web limit; allowance indicator.
- FR-04 Harmonisation: rsID+allele matching, build inference/liftover (MungeSumstats), palindromic handling with EAF, EAF-vs-reference flip check, unit standardisation (per-SD) where EAF and N allow.
- FR-05 Overlap assessment: cohort registry + cross-trait LDSC intercept; suggest non-overlapping alternatives.

**Instruments**
- FR-06 Instrument selection with defaults (P < 5×10⁻⁸, clump r² < 0.001, 10 000 kb, matched 1000G panel) and advanced overrides; LD proxies (r² ≥ 0.8) for missing outcome SNPs; optional Steiger filtering.
- FR-07 Local clumping/LD via PLINK (`ieugwasr::ld_clump(bfile=, plink_bin=)`); no API needed for LD.
- FR-08 Strength metrics: F, conditional F (MVMR), I²GX; flagged per rules R23–R24.

**Methods & feasibility**
- FR-09 Method registry read from `mr_methods.csv`; each method implemented as an **adapter** with a common input (harmonised table + settings) and output (estimate, SE, CI, P, n_IV, diagnostics, plots, warnings).
- FR-10 Feasibility engine implementing `mr_feasibility_rules.csv` at selection stage and data stage; greyed methods show the reason; amber = allowed with warning.
- FR-11 Presets: *Quick* (IVW-MRE, Egger, weighted median, weighted mode + Q, intercept, Steiger, F); *Standard* (Quick + MR-PRESSO, ConMix, MR-RAPS, MR-cML, dIVW, leave-one-out, I²GX); *Comprehensive* (all feasible v1 methods).
- FR-12 Recommender: uses data-stage diagnostics (weak IVs → dIVW/pIVW/RAPS; heterogeneity → robust set; overlap → MRlap/MR-APSS/CAUSE; directional pleiotropy → Egger/MR-cML/ConMix) informed by the benchmarks (PMIDs 39059387, 32249995).
- FR-13 Pairwise looping for univariable methods over all exposure–outcome pairs with FDR and Bonferroni options; joint models for MVMR/mediation.

**Running, results, export**
- FR-14 Background execution (`mirai`/`callr`) with progress, cancel, ETA, and per-method time-outs; heavy jobs queued.
- FR-15 Results dashboard, diagnostics panel and interpretation text (Section 3).
- FR-16 Export: HTML/PDF report (STROBE-MR structure), CSV/XLSX tables, PNG/SVG/PDF figures, citation list, recipe file.
- FR-17 Project save/reopen; re-run only changed steps (dependency-aware caching, e.g. `targets`).

**Resilience: pause, resume, crash recovery (added v1.1)**
- FR-18 Every unit of work (download, harmonisation, clumping, each method × exposure–outcome pair, each figure) is a **checkpointed task** whose state (pending / running / done / failed) is written to the project database immediately on completion. Writes are atomic (write temp file → rename; SQLite in WAL mode), so a power cut can never leave a half-written result.
- FR-19 **Pause** and **Resume** buttons in the run panel. On start-up the app detects an interrupted run and offers *Resume* (continue from the last completed task), *Restart step* or *Discard*.
- FR-20 Resumable downloads: partial files kept as `.part`, continued with HTTP range requests, verified by size/checksum before use.
- FR-21 Internet loss: the app detects offline state, pauses only network tasks, keeps running local tasks (cached data, analyses), and retries with exponential back-off when the connection returns.
- FR-22 Power protection: prevents system sleep while a run is active (macOS `caffeinate`; Windows `SetThreadExecutionState`); warns when on battery below 20%; offers "pause safely".
- FR-23 Identical results after resume: each task has a fixed seed and an input fingerprint (hash of data + settings + package versions); a task is re-used only if its fingerprint is unchanged, otherwise it is re-run.
- FR-24 Long single tasks (CAUSE, MCMC) save intermediate state where the package allows; otherwise only that task restarts.
- FR-25 UI state autosaved per step, so a crash returns the user to the same screen and selections.

**Publication support (added v1.1)** — all text is template-based (no AI); the user reviews and edits everything.
- FR-26 **Analysis-plan (pre-registration) generator** before results are shown: question, datasets, instrument criteria, primary and sensitivity methods, multiple-testing strategy; exported for OSF; time-stamped and locked. Later changes are recorded in a **deviations log** for the paper.
- FR-27 **STROBE-MR checklist** auto-filled with where each item is reported (PMID 34698778) and flags for missing items.
- FR-28 **Draft Methods section**: data sources with accession IDs, sample sizes and ancestry; instrument selection thresholds; harmonisation; methods with assumptions and citations; software and package versions; multiple-testing correction.
- FR-29 **Draft Results text, table titles and figure legends** filled with the actual numbers and units; **suggested Limitations paragraph** tailored to the diagnostics (weak IVs, heterogeneity, overlap, ancestry, binary exposure) with wording that avoids causal over-claiming.
- FR-30 **Journal-ready figures** (quality requirements FQ-1–FQ-8 below).
  - FQ-1 **Own rendering**: all figures are drawn by `mrgui.plots` (ggplot2 + one shared house theme) from the verified numeric results; stock TwoSampleMR/MendelianRandomization plot functions are used only as numeric cross-checks, never as the final look.
  - FQ-2 **Vector first**: every figure is stored as PDF/SVG with live, editable text (fonts embedded); PNG/TIFF (300–600 dpi) and EPS are rendered from that source at export.
  - FQ-3 **Journal presets**: single, 1.5 and double column widths; minimum font ≥ 6–8 pt after scaling; line weights and panel letters (A, B, C…) set per preset. Preset values are taken from each target journal's author guidelines when the preset is built and shown with their source/date; users can edit and save their own.
  - FQ-4 **No collisions**: long trait/SNP names are wrapped or abbreviated; no overlapping text in forest, scatter or regional plots; many-method and many-exposure forest plots paginate or scale automatically.
  - FQ-5 **Scale always stated**: axis titles carry units (e.g. log-OR per 1-SD higher LDL-C); null line, CI direction and the estimate type (β, OR, HR) are explicit.
  - FQ-6 **Accessibility**: colour-blind-safe palette that also reads in greyscale (shape/linetype redundancy).
  - FQ-7 **Automated figure checks** on every export: resolution, embedded fonts, text outside plot area, minimum font size, file size. Failures are flagged before the user submits.
  - FQ-8 **Composite and special figures**: multi-panel composite (forest across methods + scatter + leave-one-out + funnel), DAG/assumptions diagram, regional/colocalisation plots, bidirectional plot. Acceptance: the user reviews a sample figure set at the end of the week-1 prototype before the rest is built.
- FR-31 **Supplementary material workbook** (Excel with a README sheet): instruments with β/SE/P/EAF/R²/F, proxies used, SNPs excluded and why, harmonised data, every method's result, all diagnostics, Steiger results, MR-PRESSO outliers, power calculation.
- FR-32 **Word (.docx) export** of Methods/Results drafts and tables (most journals require Word), plus HTML/PDF.
- FR-33 **References export** (BibTeX / RIS) for every method, package and dataset used, from the inventory DOIs.
- FR-34 **Statements generator**: data availability (dataset IDs, URLs), code availability, ethics statement for publicly available summary data, and per-dataset **consortium acknowledgement text** (stored in the catalogue, because many consortia require specific wording).
- FR-35 **Power / minimum detectable effect** reported per pair (mRnd approach, PMID 24159078).
- FR-36 **Publication-readiness check** before export: red/amber list (e.g. F < 10 not addressed; overlap not handled; ancestry mismatch; fewer than the guideline-recommended sensitivity analyses; Egger reported with I²GX < 0.9; no multiple-testing correction; deviations from the locked plan not explained).
- FR-37 **Reviewer-response toolkit**: one-click re-runs of common reviewer requests (alternative P/r² thresholds, Steiger filtering, outlier removal, MVMR adjustment for a suspected pleiotropic trait, non-overlapping outcome dataset, leave-one-cohort-out), with an automatic comparison table "original vs requested analysis".
- FR-38 **Version freezing**: "as submitted" and "revision 1/2" snapshots of the whole project, with a diff of what changed in methods and results.
- FR-39 **Reproducibility capsule**: zip of recipe file, `renv.lock`, Docker image tag, scripts and results, ready to upload to Zenodo/OSF to obtain a DOI.
- FR-40 **Effect-size translation**: per-SD, per natural unit (when SD known), per doubling of odds for binary exposures (PMID 30039250), and absolute-risk illustration where baseline risk is supplied.

**Drug-target (cis-MR) & colocalisation module (v1)**
- FR-41 **Gene/protein exposure picker**: search by gene symbol or protein; the app lists available molecular-QTL datasets (blood cis-eQTL, plasma pQTL, tissue eQTL) with tissue, platform (e.g. Olink/SomaScan), ancestry and N. Sources: QTL datasets hosted in OpenGWAS where available, plus UKB-PPP, deCODE, eQTLGen and GTEx summary files that the user has downloaded (some require free registration); the catalogue records the source and terms of each.
- FR-42 **cis-region definition** from GENCODE/Ensembl gene coordinates; default window ±500 kb around the gene (editable, e.g. ±1 Mb); instrument choices: top cis-variant, LD-clumped variants (default r² < 0.1 for cis), or all correlated variants with an LD matrix.
- FR-43 **Ancestry-matched LD matrix** for the region computed locally with PLINK on the matched 1000 Genomes panel; DENTIST-style consistency QC (PMID 34880243); automatic pruning when the matrix is not positive-definite (rule R32).
- FR-44 **cis-MR estimators**: cis-MRcML (`cisMRcML::cismr_cML_DP`, robust to correlated & uncorrelated pleiotropy; PMID 39025905); PC-GMM and conditional likelihood-ratio test for weak cis instruments (`MendelianRandomization::mr_pcgmm`, `mr_clr`; PMID 37337418); IVW/Egger with correlated variants (`mr_ivw(correl=)`); Wald ratio for single top variant. **[functions verified in NAMESPACE]**
- FR-45 **SMR + HEIDI** (PMID 27019110) for single-top-variant molecular MR and the HEIDI test of linkage vs pleiotropy. Note: the official SMR binaries differ by OS (macOS arm64 1.4.2; Windows 1.3.1 — [SMR download page](https://yanglab.westlake.edu.cn/software/smr/)), which would break cross-computer reproducibility. Requirement: implement the SMR statistic and HEIDI in R inside `mrgui.core` (closed-form, published formulas), validated against both binaries; record the version used.
- FR-46 **Colocalisation** for every significant gene/protein–outcome pair: `coloc::coloc.abf` (single causal variant; PMID 24830394), `coloc::coloc.susie` with `susieR::susie_rss` fine-mapping (multiple causal variants; PMIDs 34587156, 37220626) and `hyprcoloc::hyprcoloc` for several traits at once (PMID 33536417). Results shown as posterior probabilities PP.H0–PP.H4 with the default evidence threshold (PP.H4 ≥ 0.8, editable) and a regional (LocusZoom-style) plot of both signals. **[functions verified]**
- FR-47 **Drug-target evidence summary** per gene/protein: cis-MR estimate, colocalisation PP.H4, HEIDI result, direction relative to the drug's mechanism (user enters "inhibitor/activator"), and multiple-testing correction across all genes/proteins tested (proteome-/transcriptome-wide FDR and Bonferroni); exported as a ranked table and volcano/Manhattan-style plot.

**Bidirectional MR & genetic-correlation module (v1)**
- FR-48 **Genetic correlation (rg)** between every exposure–outcome pair with cross-trait LD score regression via `GenomicSEM::munge` + `GenomicSEM::ldsc` (R, so it runs on Windows without Python; PMIDs 26414676, 30962613); outputs rg, SE, P, heritability (h²) of each trait and the cross-trait intercept (also re-used for the sample-overlap estimate, FR-05). Requires full summary statistics and matched LD scores.
- FR-49 **Reverse-direction option**: one tick runs every selected v1 method in the outcome → exposure direction with instruments selected for the outcome, and shows forward vs reverse side by side; Steiger directionality for both directions.
- FR-50 **Bidirectional MR-cML** (`BiDirectCausal::BiDirMRcML`, plus `BiDirCDcML`/`BiDirCDMethod` for causal-direction determination; PMID 35576237) — robust to correlated pleiotropy when both directions may be causal. **[functions verified]**
- FR-51 **LHC-MR** (`lhcMR::lhc_mr`; PMID 34907193) — genome-wide model estimating both causal directions and a latent heritable confounder simultaneously; heavy, runs in background. **[function verified]**
- Interpretation panel: combines rg, forward/reverse MR, Steiger, LHC-MR and Bidirectional MR-cML into one "direction of effect" summary with plain-language wording that distinguishes shared genetics (rg) from causation (MR).

### A. Project folder and structure (request 1 and 2)
- FR-52 **One folder per study.** Creating a study creates its project folder immediately, in a location the user selects with a folder picker (the "Output folder" step of New study; the first-run wizard sets the default, and it can be changed per study and in Settings). Default: a folder named `MR Studio` directly in the user's home folder (Mac `~/MR Studio/`, Windows `C:\Users\<name>\MR Studio\`). It is deliberately not inside Documents or Desktop, because iCloud Drive and OneDrive often redirect those folders and sync tools can corrupt the SQLite database (contracts C9). The same checks apply to any folder the user picks: refuses cloud-synced, network and removable drives with an explanation; tests write permission and free space; warns when the full path is longer than about 80 characters (Windows 260-character limit); never overwrites an existing folder (adds a numeric suffix).
- FR-53 **Structure.** The study folder holds one numbered sub-tree per exposure-outcome pair, so the number of pair folders follows the number of exposures and outcomes selected. Bidirectional runs add a `forward` and a `reverse` sub-folder inside the pair. Joint analyses (multivariable, mediation) get a joint folder `J01_...` instead of a pair folder. Drug-target analyses get one folder per gene or protein.

```
<Study name>/
  00_START_HERE.html          what is in this folder, how to re-run, manifest summary
  01_study_plan/              analysis plan (FR-26), deviations log, recipe file
  02_datasets/                dataset cards, import reports, missing-data ledgers,
                              checksums of originals; user-uploaded files (copy) live here
  03_pairs/
    P01_<exposure>__to__<outcome>/
      01_data/                instruments.csv, harmonised_data.csv, dropped_snps.csv,
                              analysis_data_<method>.csv (one per method, FR-83), data_dictionary.csv
      02_scripts/             00_run_all.R, NN_<method>.R, <pair>.Rproj, renv.lock,
                              session_info.txt, README_RERUN.md
      03_console/             NN_<method>_console.txt (full R console output)
      04_tables/              results per method (CSV, XLSX), diagnostics tables
      05_figures/             PDF + SVG (source), PNG/TIFF (rendered)
      06_method_reports/      NN_<method>_analysis.html (beautiful script + outputs, FR-82)
      07_replay_check/        replay_report.json, replay_report.html
      08_outlier_analysis/    flagged SNPs, scenarios, comparison tables and figures, scripts (Part H)
    P02_...
  04_across_pairs/            multiple-testing tables, summary forest plots
  05_report_and_supplement/   STROBE-MR report, supplement workbook, Methods draft, citations
  06_reproducibility/         capsule (FR-39), MANIFEST.csv (sha256 of every delivered file)
  archive/                    earlier runs, never deleted automatically
  .engine/                    project.sqlite, blobs/, logs/  (internal, hidden)
```
- FR-54 **Naming.** Folder and file names use an ASCII slug of the trait name (spaces to underscores, special characters removed, maximum 40 characters) plus a short dataset ID; the readable trait name is kept in metadata and shown in the app. Pattern: `<pair id>_<method>_<content>_v<run>.<ext>`, for example `P01_ivw_mre_results_v1.csv`. Slug collisions get a short suffix. No spaces in script names, so scripts run unchanged in a terminal.
- FR-55 **Visible files versus internal store.** The internal store (`.engine/`, contracts C9) stays as designed. Every file in the numbered folders is a real file (no symlinks, which are unreliable on Windows), written atomically when its task completes and listed in `MANIFEST.csv`. If a user edits or deletes a delivered file the app notices through the manifest and offers to regenerate it; it never overwrites a file the user changed without asking (the new version is saved beside it). Re-running a pair or method with changed settings moves the earlier outputs to `archive/run_<date_time>/`. A "Back up this study" button writes a single zip.

### B. Re-runnable script and the replay check (request 3)
- FR-56 **One script set per pair, public packages only (decided 2026-11-01).** `02_scripts/` contains a master `00_run_all.R` and one `NN_<method>.R` per selected method. Every statistical calculation in a script comes from a public, versioned R package function called directly with all arguments written out. No statistical step is hidden in app-only code. Small non-statistical glue (reading the CSV, formatting a table) is written out visibly in the script or in a short `helpers_inline.R`. The one exception is a method with no public R implementation (SMR and HEIDI, FR-45): its code is included in full, readable, inside the script, and must first be validated against the official reference program on test data. The scripts read only the CSV files in `01_data/`, write only to the pair folder and use relative paths. A guard at the top stops with a clear message if the working directory is wrong; the included `.Rproj` file opens the correct directory in RStudio.
- FR-57 **The app runs the same script it hands over.** The adapter generates each script from the method settings object; the engine executes that generated script in a clean R process and reads the outputs back. Because there is no second code path, the script cannot drift from what the app did. [proposed contract change: adapter interface C6 gains `emit_script()`; result object C7 stores the script hash and the replay status]
- FR-58 **Rerun kit.** `renv.lock` (exact package versions), `session_info.txt` (R version, OS, BLAS), seeds written in the script, and `README_RERUN.md` with the exact steps for RStudio: open the `.Rproj`, run `renv::restore()` once, then run `00_run_all.R` line by line or as a whole. The README names the R version used (4.5.x) and states that other R versions can give small numerical differences.
- FR-59 **Automatic replay check.** When a pair finishes, the app starts a fresh R process (`--vanilla`) on a temporary copy that contains only the delivered files, runs `00_run_all.R` from top to bottom, and compares every numeric output (estimates, SEs, CIs, P values, Q, intercepts, n instruments) with the stored results. Pass criterion on the same computer: identical to 15 significant digits (bit-identical for deterministic methods). Across operating systems: within 1e-8 relative (C8.6). Stochastic methods (MR-PRESSO, bootstrap-based weighted median and mode, CAUSE, MCMC) must use a fixed seed and single-threaded execution and pass the same test; if a method cannot be made identical it is labelled "reproducible to Monte Carlo error" with its tolerance, seeds and number of draws stated. The result is stored as a badge per method ("Replay verified", date, R version) and as `07_replay_check/`. A failed replay shows red and counts as a red item in the publication-readiness check (FR-36).
- FR-60 **Test of the whole chain.** CI regenerates the scripts and runs the replay check for every adapter on macOS and Windows. Acceptance (Section 11, criterion 10): on a second computer with ordinary R and RStudio, a user following only `README_RERUN.md` reproduces the app's numbers.

### C. Method customisation (request 4)
- FR-61 **Customise button** on every selected method (Methods screen). It opens a panel listing that method's adjustable arguments, grouped (Estimation, Weights, Bootstrap and seed, Output).
- FR-62 **Declarative parameter schema.** The per-method config table (also used to generate the adapters) holds, for every adjustable argument: package argument name, plain-language label, type (choice, number, integer, yes/no), allowed values or range with step, default and why it is the default, recommended range, "hint" text, reference (PMID or manual page), dependencies on other arguments or on data properties (for example "only if more than 10 instruments"), and the feasibility rules it can trigger. The panel is generated from this table, so no screen is hand-built per method.
- FR-63 **Controls follow the type.** Arguments with a fixed set of choices are dropdowns or radio buttons offering only those choices. Yes/no arguments are toggles. Numbers are bounded inputs (hard limits block entry; values outside the recommended range but inside the hard limits are accepted with an amber warning). No free-text entry for method arguments.
- FR-64 **Information icon.** A small circled "i" beside every argument opens a short popover: what it does, default and why, typical range, when you would change it, what changes in the results, and a reference link. Also reachable by keyboard.
- FR-65 **Scope rule: conventionally adjustable arguments only.** An argument is exposed when (a) it is a documented user-facing option of the package function and (b) it is used in published MR practice or in the guidelines (PMID 32760811). Never exposed: data inputs, internal numerical tuning, anything that would break the contracts (allele coding, units, sign convention). The exposed list per method is decided once, reviewed, and recorded with its source in the config table.
- FR-66 **Defaults and safety nets.** Each argument shows its default; a "changed" badge marks edits; "Reset to default" per argument and per method; **"Compare with default"** (decided 2026-11-01) runs the method with the default and with the customised settings and shows both results side by side in a table and forest plot, saved in the method's folder; settings can be copied to other pairs or saved as a named preset ("my lab settings").
- FR-67 **Live consequences.** After each change the feasibility engine re-evaluates (for example a stricter p-threshold changes instrument count and F). Every change is written to the deviations log (FR-26) and to the draft Methods text (FR-28).
- FR-68 **Own instrument set per method, only where scientifically accepted (decided 2026-11-01).** All methods of a pair share one instrument set by default. A method may have its own instrument settings only when its own literature or package documentation supports a different selection (for example weak-instrument-robust methods such as MR-RAPS or dIVW that are commonly run with a relaxed p-threshold, and methods that require an independent or a correlated set). Each permitted deviation is listed in the config table with its justification and reference, is shown in the Customise panel with an information icon, creates a separate analysis dataset for that method (FR-83) and is stated in its script and report. Arbitrary per-method instrument choices outside this list are not offered.
- FR-69 **The script mirrors the settings.** Every argument is written explicitly in the function call; defaults carry the comment `# default`, edited values `# changed from default (<default>)`.

### D. Missing and invalid values (request 5)
Principles: effect estimates (`beta`, `se`) are never invented; every repair is flagged in `qc_flags`; every drop is counted by reason in a **missing-data ledger** (`02_datasets/<dataset>_ledger.csv`, plus `dropped_snps.csv` per pair); nothing is silent. Contracts C2.2 already drops rows with missing `beta`, `se`, alleles or position; the table refines this.

| Missing or invalid | What the app does | Condition and flag |
|---|---|---|
| `rsid` missing | Keep the row; identity is `chr:pos:ref:alt`. Look up rsID from the reference panel by position and alleles | New flag 2048 when mapped; unmapped rows stay (used by position) |
| `rsid` present, position missing | Look up position (GRCh37) from the reference by rsID | Flag 16 family; if not found, drop and count |
| Neither usable ID nor position | Drop | Reason code `NO_LOCUS` |
| Effect allele missing | Drop | `NO_EA` |
| Other allele missing | Infer from the reference panel for non-palindromic biallelic sites; otherwise drop | New flag 256; palindromic or multi-allelic: drop |
| `eaf` missing | Allowed. Palindromic SNPs cannot be oriented without it: drop them (default) or fill from the ancestry-matched reference when the ancestry matches and the SNP is not close to 0.5 (user choice). Methods needing EAF (Steiger, per-SD standardisation, SMR) fill from reference with a flag, or are locked if impossible | New flag 512; setting "Strict / Standard (default) / Lenient" |
| `se` missing | Derive from `beta` and `p` (or from OR confidence limits); never from guesses | New flag 1024; if impossible, drop |
| `p` missing | Compute from `beta`/`se` | Existing flag 4 |
| `beta` missing but z-score and N present | Allowed only for methods that accept standardised effects; marked "standardised scale" in the dataset card | Flag 1024, card note |
| `p` = 0 or underflow | Recompute in log scale from z; keep `log10p` | Flag 4 |
| `n` missing per variant | Use dataset-level N from the card; if no N at all, methods needing N (MR-APSS, LDSC, MRlap, coloc, SMR) are locked with the reason | Feasibility rule |
| Case/control numbers missing for a binary trait | Ask the user at import; coloc and power need them | Import wizard |
| Instrument missing in the outcome | LD proxy (r² at least 0.8, FR-06); if none, drop and list in `dropped_snps.csv` | Counted; rule on instruments left |
| SNP missing in one dataset of a joint model | Keep the intersection; report counts per dataset | Rule on shared instruments |
| `NA`, `.`, empty, `Inf`, text in numeric columns | Treated as missing; never converted to 0 | Counted per column |
| Too many repairs or drops | More than 20% of rows dropped, or more than 30% of instruments lost: WARN; more than 50% of rows: BLOCK with explanation (thresholds are [design] heuristics, to be calibrated like the others) | New rules (R42 onward, numbers assigned when added) |

Methods receive complete cases only; the analysis dataset per method (FR-83) shows exactly which rows were used.

- FR-75 **Reproducibility of imports.** The recipe stores the original file name, size, sha256, the column mapping and the facts form; the harmonised dataset is stored in the project (`02_datasets/`). The capsule includes the harmonised copy only when the user allows it. Column mappings can be saved as templates for the same consortium layout.
- FR-76 **Privacy.** User data never leaves the computer; the importer contacts no network service except the allowed reference downloads (S-04).
- FR-77 **Column-mapping templates (decided 2026-11-01).** After a successful import the user can save the confirmed mapping and facts form as a named template (for example "FinnGen R12", "UKB-PPP", "my lab BOLT-LMM"). The template stores the header fingerprint (the set of normalised column names); when a later file has the same or a near-identical fingerprint, the app proposes the template and imports in one click, still showing the preview and any differences. Templates can be exported and shared as small files.
- FR-78 **Headings in a different spelling, abbreviation or order.** Column order never matters: columns are matched by name and by content, not position. Matching has three layers, applied to every column: (1) normalised synonym dictionary (case, spaces, punctuation and prefixes ignored, for example `P-value`, `pval`, `P_BOLT_LMM_INF`, `p.value`); (2) fuzzy matching for misspellings and unfamiliar abbreviations, which only ever produces a suggestion with a confidence score; (3) content checks on the values (for example `rs` followed by digits looks like an rsID; single letters A, C, G, T look like alleles; values strictly between 0 and 1 may be frequency or P; large integers look like positions; positive small numbers look like standard errors; numbers centred on zero look like effects). High-confidence matches are pre-filled, medium and low ones are left for the user to pick from a dropdown of the allowed roles, and the preview shows the first rows under each assignment. These pairs are never auto-confirmed and always need an explicit user choice: effect allele versus other allele (A1/A2), effect-allele frequency versus minor-allele frequency, beta versus odds ratio versus z-score, P versus -log10(P), and two candidate columns for the same role (for example two P columns). Columns that match no role are listed as "ignored" in the import report. Files without a header row are accepted only after the user chooses a known layout or defines the column order.
- FR-79 **A whole column is missing.** The import report shows a traffic light per field for each role (exposure, outcome, and so on) before anything is saved:
  - Cannot continue: effect allele; effect size (at least one of beta, odds ratio with limits, or z-score with N and frequency); no way to place the variant (neither rsID nor chromosome and position).
  - Derived from other columns, flagged: any one of beta, SE and P from the other two; log odds ratio and SE from odds ratio and confidence limits; position from rsID or rsID from position (reference panel); other allele from the reference for non-palindromic biallelic variants.
  - Can be supplied by the user: N, cases and controls, genome build, ancestry, effect scale and units (study facts form, FR-72).
  - Can be filled from the reference panel, flagged: effect-allele frequency (Standard mode, decided 2026-11-01).
  - Optional: INFO, per-variant N, P when beta and SE exist.
  Every consequence is shown plainly, for example "no EAF: Steiger and per-SD scaling will use reference frequencies; palindromic SNPs near 0.5 are dropped" or "no N anywhere: MR-APSS, LDSC and colocalisation are locked until you enter N". The user may also attach a companion file (for example a separate frequency or position file released by the consortium) that is joined by variant ID. Nothing proceeds silently: the user confirms the report before the dataset joins the catalogue.

### H. Outlier detection, comparison and removal (requested 2026-11-01)
Purpose: when heterogeneity or horizontal pleiotropy is detected, find candidate outlier instruments with several independent detectors, test every detector's proposal by removing the SNPs and re-analysing, compare the proposals openly in a table and a forest-style figure, choose one by a rule that is fixed in advance, and continue the remaining steps with the chosen set while keeping the all-instrument results visible. All thresholds below are [design] heuristics to be calibrated by simulation before release (FR-104), like the other thresholds in the inventory.

- FR-90 **Diagnostics always, removal only on a signal.** For every pair the app always reports Cochran's Q and I² (guidelines: report a heterogeneity measure in every polygenic MR investigation), leave-one-out results and the radial or scatter plot. The outlier-removal scenarios below start only when at least one signal is present: Cochran's Q P < 0.05 (IVW), MR-Egger intercept P < 0.05, MR-PRESSO global test P < 0.05 (when feasible), or distinct outliers in the plots. With no signal it reports "no outlier handling needed" and removes nothing. The user can also start it manually. The trigger rule is a [design] choice; the guidelines do not prescribe one.
- FR-91 **Data-error screen first.** Before any statistical outlier is considered, instruments that look like data errors are flagged separately as data-quality candidates: allele or strand problems (EAF clearly discordant with the reference), implausible SE, low INFO, ambiguous palindromes, and wrong direction by Steiger. Steiger filtering is a pre-specified filter (FR-06) applied before the detectors; it is not one of the competing detectors.
- FR-92 **Detectors.** Each runs with its package's native definition, once, with its package defaults (adjustable in the Customise panel, FR-61): MR-PRESSO outlier test (`MRPRESSO::mr_presso`, with global and distortion tests); Radial IVW outliers (`RadialMR::ivw_radial`); Radial Egger outliers (`RadialMR::egger_radial`); MR-Lasso, using the instruments the penalisation treats as invalid (`MendelianRandomization::mr_lasso`). All four are catalogued as verified in `mr_methods.csv` (function names verified in NAMESPACE; the exact output fields that list the flagged SNPs are verified when the adapters are written). A detector that cannot run (for example MR-PRESSO needs more instruments than exposures plus 2 and NbDistribution above the number of instruments, rule R31) is listed with the reason. Cook's distance and studentised residuals are not in the verified inventory and are left out until their method reference is verified. MR-Clust cluster membership can be shown as extra information, not as a detector. **Caution carried into the interface (guidelines, Table 1, citing the simulation study of Slob and Burgess):** MR-PRESSO and MR-Lasso remove outliers and are efficient when the other variants are valid, but have a very high or high false-positive rate when several instruments are invalid; this text is shown in the information icon of each detector and in the report. Radial MR outlier detection is supported by Bowden 2018 (PMID 29961852) and is not described as a removal method in the guidelines, which mention radial plots only as a way to assess heterogeneity.
- FR-93 **Flag ledger.** `outliers_flagged.csv` has one row per instrument and detector: variant ID, rsID, chromosome and position, nearest gene (from the bundled GENCODE data), weight and F, the detector's own statistics (for example PRESSO observed residual sum of squares and P, radial Q contribution and P, Lasso status), flagged yes or no, number of detectors that flagged it, whether it is removed in the selected set, and the reason it was not removed (cap, floor, not selected). Data-quality candidates are listed in the same file with their own column.
- FR-94 **Candidate sets.** S0 = all instruments. One set per detector (the instruments that detector flags), and a consensus set (flagged by at least two detectors, when any exist). The union of all detectors is not offered by default because it over-removes.
- FR-95 **Safeguards.** (a) Cap: a set may remove at most 20% of the initial instruments; a larger set stays in the comparison labelled "over cap, not eligible". (b) Floor: enough instruments must remain for every method still to be run (feasibility engine), and never fewer than 5; a set that would lock a selected method is not eligible unless the user accepts the loss. (c) Strength: F, conditional F and I²GX are recomputed; a set that pushes them below the rule thresholds (R23, R24) is amber. (d) One round per detector; iterating until nothing is flagged is off by default because it over-removes. (e) The choice never uses the causal estimate or its P value. (f) P values for Q and the Egger intercept after removal are descriptive only, because choosing which SNPs to remove makes them optimistic; tables and figures say so.
- FR-96 **Re-analysis of every eligible set.** For S0 and each eligible set the app re-runs: IVW multiplicative random effects, Cochran's Q with degrees of freedom and I² ((Q-df)/Q), Rücker's Q', Q minus Q', MR-Egger intercept (estimate, SE, P), MR-PRESSO global test (when feasible), and for transparency the IVW, MR-Egger and weighted-median causal estimates; plus number of instruments, F and I²GX. Every run is a checkpointed task with its own script and its own analysis dataset, and is covered by the replay check.
- FR-97 **Comparison table** (`outlier_comparison.csv` and `.xlsx`): one row per scenario (all instruments; after the PRESSO set; Radial IVW set; Radial Egger set; MR-Lasso set; consensus; selected). Columns: number removed and their IDs, Q, df, Q P (descriptive), I², excess heterogeneity (Q-df), change in Q against the full set, **excess reduction (change in Q minus number removed)**, Egger intercept with CI and P, PRESSO global P, F, I²GX, the three causal estimates with CI (shown, not used for selection), eligibility, and the decision. Excess reduction exists because removing k typical instruments lowers Q by about k even when nothing is wrong, so only a reduction beyond k is evidence that real outliers were removed. The table and figure also carry, as reference lines on the full instrument set, the estimates of the robust methods that do not remove variants (weighted median, mode-based estimate, contamination mixture, MR-cML and MR-RAPS where feasible), so that the user can see whether the outlier-removed estimate agrees with methods based on other assumptions (guidelines: a range of analyses depending on different assumptions).
- FR-98 **Comparison figures** in the house style (FQ-1 to FQ-8): a multi-panel forest-style figure with the scenarios as rows: causal estimate with CI, heterogeneity (I² and excess heterogeneity), Egger intercept with CI and null line, MR-PRESSO global P; points with intervals where an interval exists, dots otherwise. Also an agreement plot showing which SNPs each detector flagged, the radial plot with outliers marked, and leave-one-out before and after. Saved as PDF, SVG and PNG.
- FR-99 **Selection rule** (fixed before results are seen and written into the analysis plan, FR-26). Consider eligible sets only. Step 1: keep the sets after which every signal that triggered the module (FR-90) is no longer present, evaluated descriptively. Step 2: among them choose the one that removes the fewest SNPs; ties go first to the set with higher detector agreement, then to larger excess reduction. Step 3: if no set clears the signals, choose the eligible set with the largest positive excess reduction; if none improves on the full set, keep all instruments and report "no eligible improvement". The rule is part of the locked analysis plan; all scenarios are reported whether or not they are selected (guidelines: selective reporting must be avoided and all analyses performed described transparently). The rule itself is a [design] choice; the guidelines give no rule for choosing among outlier sets.
- FR-100 **Primary analysis stays pre-specified; the cleaned set drives a labelled sensitivity branch (settled 2026-11-01 following the guidelines).** The guidelines ask that primary analyses are specified in advance and recommend the multiplicative random-effects IVW as the default, with outlier-removing methods listed among the robust sensitivity analyses. Therefore: the primary analysis is whatever the locked plan (FR-26) names, by default IVW (multiplicative random effects) on all instruments. The selected outlier-removed set becomes the working set of a second branch: the remaining sensitivity methods, diagnostics and figures are run on it as well as on the full set, results are shown side by side labelled "all instruments" and "after outlier removal (data-driven sensitivity analysis)", and heavy methods (CAUSE, MCMC) run on the full set only unless the user ticks otherwise. A user who wants the cleaned set to be the primary analysis must say so in the plan before results are seen, and the report then states that it was pre-specified. The deviations log and the draft Methods state the detectors, thresholds, removed SNPs and the rule.
- FR-101 **Folder.** `03_pairs/Pxx_.../08_outlier_analysis/` with `01_flagged/`, `02_scenarios/` (one analysis CSV per scenario), `03_tables/`, `04_figures/`, `05_scripts/`, `06_console/` and `07_report.html`.
- FR-102 **Review before adoption (settled 2026-11-01).** A review screen shows the flagged SNPs per detector, their trait associations (FR-112) and nearest genes, the comparison, the app's selection and the reason, and lets the user choose another eligible set, keep all instruments, or enter a manual SNP list before the cleaned branch runs. In unattended runs the rule applies automatically and the result is flagged "awaiting review".
- FR-103 **Text.** Template sentences for Methods and Results, and a Limitations paragraph that states that outlier removal is a data-driven sensitivity analysis, that heterogeneity can reflect real biology of valid instruments and not only pleiotropy, and that removal can shift estimates.
- FR-104 **Validation before release.** A simulation study covering no pleiotropy, balanced pleiotropy, directional pleiotropy, valid but heterogeneous instruments, few and many strong outliers, and 10 to 200 instruments; for each detector and for the selection rule it measures bias, coverage, false-removal rate and power. The cap, floor and trigger thresholds are set from it. Unit tests reproduce published outputs of MR-PRESSO and RadialMR on their package example data.
- FR-105 **Leave-subset-out and dominant-variant checks (guidelines).** In addition to leave-one-out, when there are many instruments the app runs repeated leave-out of random subsets (default 30% at a time, with a fixed seed and a stated number of repeats) and shows the spread of the estimate; it reports the share of total weight carried by the strongest instrument and the estimate without it (guidelines: assess robustness to removing a variant that dominates the estimate, and leaving out subsets may be more appropriate than one at a time when there are many variants). Results are saved in `08_outlier_analysis/`.
- FR-106 **Horizontal versus vertical pleiotropy reminder (guidelines).** The review screen states that removing horizontally pleiotropic variants should give more reliable results, whereas removing vertically pleiotropic variants (those acting through the exposure pathway, typically associated with many exposure-related traits) can distort the causal estimate. Each flagged SNP shows whether it is associated with many exposure-related traits (FR-112) so that the user can judge which kind of pleiotropy is likely; the app does not decide this automatically.


### I. Additional methodological safeguards (added 2026-11-01, each checked against the literature)
Evidence check (PubMed and the full text of the 2023 guidelines, 2026-11-01): the guidelines of Burgess et al. (PMID 32760811) support items FR-110 (comparability of the two samples in age and sex, and subgroup analyses), FR-111 (winner's curse and selecting variants in a separate dataset), FR-112 (examining associations of the variants with potentially pleiotropic variables), FR-113 (population structure, assortative mating and dynastic effects, and within-family analysis where a dataset is available), FR-114 (replication in an independent dataset, varying the dataset, triangulation), FR-115 (positive and negative control outcomes) and FR-116 (estimates reflect long-term exposure differences). Supporting primary or review papers: Brumpton 2020 (PMID 32665587), Davies 2019 (PMID 31647093), Howe 2022 (PMID 35534559), Rawlik 2016 (PMID 27473438), Lawlor 2016 (PMID 28108528), Sanderson 2022 (PMID 37325194), PhenoScanner (PMIDs 27318201, 31233103). Where a point below goes beyond what these papers state, it is marked [design].

- FR-110 **Sex of the samples.** The dataset card gains `sex` (both, female, male, unknown) and optional `age_range`; the catalogue can be filtered by sex and the Data screen shows a sex badge. When the exposure and outcome samples differ in sex (for example a both-sex exposure with a female-only outcome) the feasibility engine gives an amber warning, not a block, citing the guideline point that differences in age, sex and similar characteristics between the two samples can affect the interpretation and validity of the estimate, and the evidence for genetic heterogeneity between sexes in many traits (PMID 27473438). The app offers sex-matched datasets where the catalogue has them. Where sex-specific datasets exist for both traits, a sex-stratified run (female and male separately, side by side) can be requested; it is offered, not default [design]. The limitations text states the mismatch.
- FR-111 **Winner's curse and where instruments are selected.** The dataset card records whether a dataset was used to select instruments, to estimate their exposure effects, or both. The instrument step offers "select in dataset A, estimate effects in independent dataset B", checked for cohort overlap (FR-05). When selection and estimation are in the same dataset the app shows a banner explaining that associations tend to be overestimated in the dataset in which they were discovered and that weak-instrument bias is exacerbated, and reports the number of instruments and mean F under each choice, because a smaller selection dataset can cost power. The catalogued methods that were proposed to reduce weak-instrument, overlap and winner's curse bias are recommended in the banner only after each method's own paper has been checked for which of the three biases it addresses (done once per method in the config table).
- FR-112 **Associations of the instruments with other traits.** For every instrument the app lists its associations with other traits above a user-set threshold, from the local cache of downloaded GWAS, cached GWAS Catalog associations and OpenGWAS when reachable; PhenoScanner (PMIDs 27318201, 31233103) is used only if its service is reachable at the time, which must be checked when this is built. Output: `instrument_trait_associations.csv` and a plain-language summary with the coverage and date of each source, stated as incomplete when offline. The user supplies the list of traits considered potential confounders for the question (the app may suggest but never hard-codes one, because this is a scientific judgement per question). Uses: shown in the outlier review (FR-93, FR-102); an optional, labelled sensitivity analysis that excludes instruments associated with the chosen traits; a pointer to multivariable MR for traits that matter [design].
- FR-113 **Family-level bias.** The card gains `design` (population or within_family) and a `socially_patterned` flag (default unknown, set by the catalogue curators or the user). For flagged traits the app shows an INFO rule citing the guideline text (population structure, assortative mating and dynastic effects are greater concerns for socially patterned traits) and the limitations paragraph. Within-family summary statistics (Brumpton 2020; Howe 2022; PMIDs 32665587, 35534559) are supported as a dataset type; they are added to the catalogue only after the availability and licence of each specific dataset has been verified. Where a within-family version exists, the pair can be run in the population and the within-family data side by side, with a note that within-family analyses typically have lower power.
- FR-114 **Replication and triangulation.** "Add replication pair" repeats the same question with an independent exposure and/or outcome dataset. Cohort overlap between the datasets is checked first (FR-05); overlapping cohorts block the combined analysis and get a warning in the side-by-side view. Results appear in one forest plot with a concordance table (direction, estimates, CIs, heterogeneity between datasets); a fixed-effect combination of the two estimates is offered only when the datasets are independent and on the same scale and units. The app does not declare success or failure of replication beyond describing concordance [design]. Report templates include the triangulation paragraph (PMID 28108528) and state that replication does not remove uncertainty in the instrumental variable assumptions.
- FR-115 **Control outcomes.** The user can add a positive control outcome (an outcome for which the exposure is established as causal) and/or a negative control outcome (an outcome believed not to be caused by the exposure) to a pair, with a required free-text justification and source. The app runs the same instruments and methods on them and reports them in a control-outcomes table and forest plot with the guideline interpretation: an apparent effect on a negative control suggests a violation of the instrumental variable assumptions, and a null result on a positive control with adequate power questions whether the variants proxy the exposure. The app never chooses control outcomes itself.
- FR-116 **Wording rule.** All interpretation, Methods and Limitations templates state that estimates reflect the effect of long-term differences in the exposure as proxied by genetic variants, not the effect of a short-term intervention, and that effects at specific life stages are not identified unless time-varying MR is used (not in v1).
- FR-117 **End-to-end replication test.** Before release, at least one published MR study with public summary data (for example one of Dr. Habibi's papers) is reproduced end to end in the app; every number in the paper's main tables and figures is compared with the app's output within a stated tolerance, and every difference is explained (for example a newer data version).
- [proposed contract change] C3 dataset card gains `sex`, `age_range`, `design`, `socially_patterned`, `selection_role`; new feasibility rules (numbers assigned when added): sex mismatch (WARN), instruments selected and estimated in the same dataset (WARN), overlapping cohorts in a replication pair (BLOCK for the combined estimate, WARN otherwise), socially patterned trait (INFO).

## 9. Architecture and packaging (desktop app)
- **Desktop shell: Tauri 2** (small, secure Rust-based wrapper; native window on macOS and Windows). The R engine is shipped as a bundled **sidecar** process that the shell starts and stops ([Tauri sidecar docs](https://v2.tauri.app/develop/sidecar)). Electron is the fallback if a blocking issue appears in prototyping.
- **Engine**: R package `mrgui.core` (catalogue, harmonisation, instruments, feasibility engine, method adapters, report builder) + Shiny UI rendered inside the desktop window; the server listens on `127.0.0.1` with a random port and a per-session secret, so no other program or computer can connect.
- **Bundled R runtime: conda-forge R** (r-base builds exist for win-64, osx-arm64 and osx-64; v4.6.1 at time of writing — [conda-forge r-base](https://prefix.dev/channels/conda-forge/packages/r-base)) installed into the app's own folder, so the user never installs R and no admin rights are needed. All CRAN and GitHub MR packages are **pre-compiled in CI** for each OS and bundled — the user never compiles anything.
- **Bundled tools**: PLINK 1.9 and PLINK 2 official binaries per OS (clumping, LD matrices, proxies); SMR/HEIDI implemented in R (FR-45); GCTA optional in v2.
- **Jobs & resume**: `mirai`/`callr` workers; checkpointed task graph (FR-18–25).
- **Storage**: user-chosen project folder = SQLite (WAL) metadata/results + Parquet harmonised data (Data library tables, written with nanoparquet since Round 35; files the analyst opens stay CSV) + figures/reports; reference data in a shared app-data folder.
- **Build pipeline**: private GitHub repo; GitHub Actions builds the `.dmg` (macOS arm64 + x64) and `.exe` (Windows x64) installers, runs the full test suite on both, and publishes releases.
- **Fallback plan**: if bundling conda-forge R fails for a package on one OS during the prototype, use the official CRAN R installer silently into a per-user folder (Windows supports non-admin installs) — decided in week-1 prototype.

4. A recipe file created on one machine reproduces the analysis on the other.
5. No token, individual-level data or personal information appears in any exported file or log.
6. Killing the app (or pulling the power) mid-run and pressing **Resume** finishes the analysis with results identical to an uninterrupted run.
7. A drug-target analysis (one protein → one disease) runs end-to-end on both computers: cis-MR, colocalisation (PP.H4), HEIDI and a regional plot, with identical numbers on macOS and Windows.
7b. Genetic correlation, forward and reverse MR and Bidirectional MR-cML for one trait pair complete and are summarised in one direction-of-effect panel.
8. A non-technical user installs the app from the `.dmg`/`.exe`, completes the first-run wizard and passes the self-test in under 30 minutes (excluding download time), with no terminal or Docker.
9. Exported Methods draft, supplementary workbook, STROBE-MR checklist and references require no manual re-typing of numbers, versions or dataset IDs.
10. For every pair, the delivered `02_scripts/` re-runs on a second computer with ordinary R and RStudio, following only `README_RERUN.md`, and reproduces the app's numbers (identical on the same OS; within 1e-8 across OS; stochastic methods with fixed seeds as stated in FR-59). The app's own replay check shows "verified" for every method of the demo study.
11. Every selected method has a Customise panel generated from its parameter schema; every choice-type argument offers only its allowed values; every argument has an information icon; a changed setting appears in the script, the deviations log and the Methods draft.
12. A messy user file from the import test pack either imports with every repair flagged and counted, or stops with a plain explanation; no row is changed or dropped without a ledger entry; top-hits-only files cannot be used as outcomes.
13. Every completed method delivers the formatted script, the analysis report, the final analysis CSV with data dictionary, the results table and the console log, in the pair's numbered folders.
14. 15. A user-supplied file with differently spelled, abbreviated or reordered headings is mapped correctly or stops at a clear question; a file with a whole required column missing shows the traffic-light report and the exact consequence for each method; a saved column-mapping template imports a second file of the same layout in one click.
